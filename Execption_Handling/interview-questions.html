🔥 Top 15 Java Exception Handling Interview Questions

1. What is exception handling in Java?

Interview answer

Exception handling is a mechanism in Java used to handle abnormal conditions that occur during program execution. It allows us to handle exceptions gracefully instead of allowing them to terminate the program unexpectedly. Java provides try, catch, finally, throw, and throws for exception handling.

For example:

try {
    int result = 10 / 0;
}
catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero");
}

The important idea is:

Problem occurs
     ↓
Exception object is created
     ↓
Matching handler is searched
     ↓
Exception is handled
     ↓
Program can continue

2. What is the difference between throw and throws?

This is extremely common.

Interview answer

throw is used to explicitly throw an exception object, whereas throws is used in a method declaration to indicate that the method may pass one or more exceptions to its caller.

throw

if (age < 18) {
    throw new IllegalArgumentException("Invalid age");
}

You're actually throwing the exception.

throws

void readFile() throws IOException {
    // file operation
}

You're declaring that the method may throw IOException.

Easy memory trick:

throw  → "I'm throwing it NOW."
throws → "This method MAY throw it."

3. What is the difference between final, finally, and finalize()?

🔥 Classic interview question.

Interview answer

final is a keyword used to restrict variables, methods, and classes. finally is a block used in exception handling that is generally executed after try/catch. finalize() was a method historically associated with garbage collection, but it has been deprecated and should not be relied upon for resource cleanup.

Examples:

final int x = 10;

The variable cannot be reassigned.

try {
    // code
}
finally {
    // cleanup
}

And finalize() is not recommended for modern Java code.

For resource cleanup, prefer:

try (Resource r = ...) {
    // use resource
}

4. What is the purpose of the finally block?

Interview answer

The finally block is used for code that should generally execute after the try and catch blocks, regardless of whether an exception occurred. It is commonly used for cleanup operations such as releasing resources.

Example:

try {
    System.out.println("Opening resource");
}
catch (Exception e) {
    System.out.println("Exception");
}
finally {
    System.out.println("Cleanup");
}

Typical use:

Open resource
     ↓
Use resource
     ↓
Exception?
   /     \
 Yes      No
 ↓        ↓
catch    continue
   \      /
    finally
       ↓
   cleanup

However, for resources like files and database connections, try-with-resources is generally preferred.

5. Is finally always executed?

This is a tricky one.

Interview answer

No, finally is not absolutely guaranteed to execute. Under normal control flow, it executes whether an exception occurs or not. However, there are situations such as JVM termination using System.exit(), JVM crashes, or the process being forcibly terminated where it may not execute.

For example:

try {
    System.out.println("Try");
    System.exit(0);
}
finally {
    System.out.println("Finally");
}

The JVM terminates, so finally does not get a chance to execute.

Interview-safe wording:

"finally executes in normal control flow, but it is not an absolute guarantee."

6. What happens if an exception occurs inside the try block?

Suppose:

try {
    System.out.println("A");

    int x = 10 / 0;

    System.out.println("B");
}
catch (ArithmeticException e) {
    System.out.println("C");
}

System.out.println("D");

Output:

A
C
D

Interview answer

When an exception occurs inside a try block, the JVM stops normal execution of the remaining statements in that try block and looks for a matching catch block. If a matching handler is found, it executes the catch block and then continues after the exception-handling structure.

So:

A
↓
Exception
↓
B skipped
↓
catch
↓
C
↓
D

7. What is exception propagation?

Interview answer

Exception propagation is the process by which an exception moves from the method where it occurred to its calling methods until a matching exception handler is found.

Example:

void methodC() {
    int x = 10 / 0;
}

void methodB() {
    methodC();
}

void methodA() {
    methodB();
}

Suppose main() calls:

try {
    methodA();
}
catch (ArithmeticException e) {
    System.out.println("Handled");
}

The flow is:

main()
  ↓
methodA()
  ↓
methodB()
  ↓
methodC()
  ↓
exception
  ↓
methodB doesn't handle
  ↓
methodA doesn't handle
  ↓
main handles

This is exception propagation.

8. What is stack unwinding?

This is closely related to propagation but not exactly the same thing.

Interview answer

Stack unwinding is the process of removing method call frames from the call stack when an exception propagates because the current method doesn't have a matching exception handler.

Imagine:

main()
  ↓
A()
  ↓
B()
  ↓
C()
  ↓
Exception

If C() doesn't handle it:

C() removed from active execution
       ↓
B() examined
       ↓
B() doesn't handle
       ↓
A() examined
       ↓
A() doesn't handle
       ↓
main() examined
       ↓
handler found

So remember:

Propagation = exception moving upward. Stack unwinding = call stack being unwound while searching upward.

🔥 This distinction makes a strong interview impression.

9. Can we have a try block without catch?

Interview answer

Yes. A try block can exist without a catch block if it is followed by a finally block.

Valid:

try {
    // code
}
finally {
    // cleanup
}

But this is invalid:

try {
    // code
}

A try must be followed by at least one:

catch

or

finally

10. Can we have multiple catch blocks?

Interview answer

Yes. We can have multiple catch blocks to handle different types of exceptions differently. The JVM chooses the first compatible catch block.

Example:

try {
    // risky code
}
catch (ArithmeticException e) {
    System.out.println("Arithmetic problem");
}
catch (NullPointerException e) {
    System.out.println("Null reference");
}
catch (Exception e) {
    System.out.println("Other exception");
}
⭐Important rule

The more specific exception should come before the more general exception.

Correct:

catch (ArithmeticException e) {
}
catch (Exception e) {
}

Incorrect:

catch (Exception e) {
}
catch (ArithmeticException e) {
}

Because:

Exception
   ↑
ArithmeticException

The first catch would already cover ArithmeticException.

11. Can we have catch without try?

Interview answer

No. A catch block must always be associated with a try block.

Invalid:

catch (Exception e) {
}

Valid:

try {
    // code
}
catch (Exception e) {
}

The same applies to finally: it cannot exist independently.

12. What happens if an exception is not handled anywhere?

Interview answer

If an exception isn't handled in the current method, it propagates up the call stack. If it reaches the top of the thread's call stack without finding a matching handler, the JVM's uncaught-exception mechanism handles it, typically printing the exception's stack trace and terminating that thread.

For example:

public static void main(String[] args) {

    int x = 10 / 0;

    System.out.println("Hello");
}

There is no handler.

So you'll typically see:

Exception in thread "main"
java.lang.ArithmeticException: / by zero

And:

System.out.println("Hello");

will not execute.

13. What is a stack trace?

Interview answer

A stack trace is information about the sequence of method calls that were active when an exception occurred. It helps identify where the exception originated and how execution reached that point.

Example:

static void methodB() {
    int x = 10 / 0;
}

static void methodA() {
    methodB();
}

You may see something like:

ArithmeticException: / by zero

at Main.methodB(Main.java:5)
at Main.methodA(Main.java:9)
at Main.main(Main.java:13)

Read it roughly from the top:

methodB()
   ↓
called by methodA()
   ↓
called by main()

The line number tells you where the exception originated.

You can manually print it using:

e.printStackTrace();

14. What is try-with-resources?

🔥 Very important for practical Java.

Interview answer

Try-with-resources is a Java feature used to automatically close resources after they are used. The resource must implement AutoCloseable. It eliminates the need to explicitly close resources in a finally block.

Traditional approach:

FileInputStream file = null;

try {
    file = new FileInputStream("data.txt");
}
finally {
    if (file != null) {
        file.close();
    }
}

Try-with-resources:

try (FileInputStream file =
         new FileInputStream("data.txt")) {

    // use file

}

Java automatically closes file.

This is commonly used with:

  • FileInputStream
  • BufferedReader
  • database connections
  • statements
  • result sets

15. What happens if both try and finally have a return statement?

🔥 This is a classic trap question.

Consider:

static int test() {

    try {
        return 10;
    }
    finally {
        return 20;
    }
}

What does it return?

20

Why?

The return 10 from try is prepared, but before the method actually completes, finally executes.

Then:

return 20;

overrides the earlier return.

Interview answer:

If both try and finally contain a return statement, the return from finally takes precedence and suppresses the return from try. However, using return inside finally is strongly discouraged because it can hide exceptions and make control flow difficult to understand.

For example:

try {
    throw new RuntimeException("Problem");
}
finally {
    return 10;
}

The exception can effectively be suppressed by the return in finally.

So:

🚨 Never use return in finally unless you have a very specific reason.

⭐ 5 Bonus Questions You Should Also Know

These are slightly more advanced and are worth preparing once the top 15 are comfortable.

16. Can we throw an exception from a finally block?

Yes.

finally {
    throw new RuntimeException("Error");
}

But it can mask an exception that was already being propagated, so it should be used carefully.

17. Can one catch block handle multiple exceptions?

Yes, using multi-catch:

try {
    // code
}
catch (IOException | SQLException e) {
    System.out.println("Operation failed");
}

This was introduced in Java 7.

18. What is a custom exception?

A custom exception is an exception class created by the developer for an application's specific situation.

class UserNotFoundException
        extends RuntimeException {

    UserNotFoundException(String message) {
        super(message);
    }
}

Then:

throw new UserNotFoundException(
    "User not found"
);

This is extremely common in Spring Boot applications.

19. What is exception chaining?

Exception chaining means preserving the original exception as the cause of another exception.

try {
    // database operation
}
catch (SQLException e) {

    throw new RuntimeException(
        "Unable to fetch user", e
    );
}

Here:

RuntimeException
      ↓
caused by
      ↓
SQLException

This lets you add higher-level context without losing the original cause.

20. What is the difference between getMessage() and printStackTrace()?

catch (Exception e) {

    e.getMessage();

    e.printStackTrace();
}

getMessage() gives the exception's message:

"File not found"

printStackTrace() gives much more information:

Exception type
Message
Call stack
Class
Method
Line number

In production applications, you would normally use a proper logging framework rather than simply calling printStackTrace().

🔥 Top 10 Interview Questions on Checked vs Unchecked Exceptions

1. What is the difference between checked and unchecked exceptions?

Interview answer:

Checked exceptions are exceptions that the compiler forces us to handle or declare using try-catch or throws. Examples are IOException, SQLException, and FileNotFoundException.

Unchecked exceptions are subclasses of RuntimeException, and the compiler does not force us to handle or declare them. Examples are NullPointerException, ArithmeticException, and ArrayIndexOutOfBoundsException.

Both exceptions occur at runtime; the term checked refers to the fact that the compiler checks whether we have handled or declared the exception.

Remember:

Checked   → Compiler forces you
Unchecked → Compiler doesn't force you

2. Why are checked exceptions called "checked"?

Interview answer:

They are called checked exceptions because the compiler checks whether the programmer has handled or declared them. If we don't use try-catch or throws for a checked exception, the code will not compile.

Example:

void readFile() {
    FileReader reader = new FileReader("data.txt");
}

The compiler complains because FileNotFoundException is checked.

We need:

void readFile() throws FileNotFoundException {
    FileReader reader = new FileReader("data.txt");
}

or:

try {
    FileReader reader = new FileReader("data.txt");
}
catch (FileNotFoundException e) {
    // handle
}
⭐Important ⚠️

Don't say:

❌ "Checked exceptions are checked at compile time and occur at compile time."

The exception occurs at runtime.

Only the requirement to handle/declare it is checked by the compiler.

3. Are unchecked exceptions checked by the JVM?

This is a slightly tricky question.

Interview answer:

No. The distinction between checked and unchecked exceptions is primarily about compiler enforcement. The JVM can throw both checked and unchecked exceptions at runtime. For unchecked exceptions, the compiler simply doesn't require us to catch or declare them.

Example:

int result = 10 / 0;

This compiles successfully.

But at runtime:

ArithmeticException

occurs.

So:

Compiler
   ↓
enforces checked exceptions

JVM
   ↓
handles exceptions during runtime

4. What happens if we don't handle a checked exception?

Suppose:

void readFile() {

    FileReader reader =
        new FileReader("data.txt");
}

Interview answer:

If a checked exception is neither caught using try-catch nor declared using throws, the program will fail to compile. The compiler reports that the exception must be caught or declared to be thrown.

For example:

unreported exception FileNotFoundException;
must be caught or declared to be thrown

So:

Checked exception
       ↓
catch OR throws
       ↓
Mandatory

5. Can we handle an unchecked exception using try-catch?

Interview answer:

Yes. Unchecked exceptions can also be caught using try-catch. The difference is that the compiler does not force us to handle them.

Example:

try {
    int result = 10 / 0;
}
catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero");
}

This is completely valid.

The important distinction is:

Checked exception
→ handling is mandatory

Unchecked exception
→ handling is optional

🔥 This is a common follow-up question.

6. Can we use throws with an unchecked exception?

Interview answer:

Yes. We can declare an unchecked exception using throws, but it is not mandatory because unchecked exceptions are not checked by the compiler.

Example:

void calculate() throws ArithmeticException {

    int result = 10 / 0;
}

This is valid.

But this is also valid:

void calculate() {

    int result = 10 / 0;
}

Because ArithmeticException is unchecked.

So:

Checked:
throws → sometimes required

Unchecked:
throws → optional

7. How do you identify whether an exception is checked or unchecked?

This is a very good interview question.

Interview answer:

We can look at the exception's position in the exception hierarchy. If an exception is a subclass of RuntimeException, it is unchecked. Exceptions that extend Exception but are not under RuntimeException are generally checked.

For example:

Throwable
   |
   Exception
   |
   RuntimeException
   |
   NullPointerException

Therefore:

NullPointerException
        ↓
RuntimeException
        ↓
Unchecked

Whereas:

Throwable
   |
 Exception
   |
 IOException

Therefore:

IOException
    ↓
Checked

Shortcut 🧠

RuntimeException → Unchecked

8. Why is NullPointerException unchecked?

This is where interviewers test whether you understand the concept rather than memorized it.

Interview answer:

NullPointerException is unchecked because it generally indicates a programming error or invalid program state, such as trying to invoke a method on a null reference. Java doesn't force developers to catch it because catching it everywhere would often hide programming bugs. Instead, the programmer is generally expected to prevent or fix the invalid state.

Example:

String name = null;

name.length();

This produces:

NullPointerException

You can catch it:

try {
    name.length();
}
catch (NullPointerException e) {
    System.out.println("Name is null");
}

But usually the better solution is to fix the underlying problem:

if (name != null) {
    name.length();
}

9. Can we create our own checked and unchecked exceptions?

🔥 Very important for real projects.

Interview answer:

Yes. We can create custom exceptions. If our custom exception extends Exception, it becomes a checked exception. If it extends RuntimeException, it becomes an unchecked exception.

Custom checked exception:

class InvalidAgeException
        extends Exception {

    public InvalidAgeException(String message) {
        super(message);
    }
}

Because it extends:

Exception

it is checked.

Custom unchecked exception:

class UserNotFoundException
        extends RuntimeException {

    public UserNotFoundException(String message) {
        super(message);
    }
}

Because it extends:

RuntimeException

it is unchecked.

Remember:

extends Exception
       ↓
Checked

extends RuntimeException
       ↓
Unchecked

10. When should you use checked vs unchecked exceptions?

🔥 This is probably the best practical interview question.

Interview answer:

Checked exceptions are generally appropriate when the caller can reasonably be expected to recover from an exceptional condition, such as an I/O operation failing or a file not being available.

Unchecked exceptions are generally appropriate for programming errors, invalid arguments, or situations where the caller cannot reasonably recover at that point. They are also commonly used for custom business exceptions in modern Java applications, including many Spring applications.

For example:

Checked

FileReader reader =
    new FileReader("data.txt");

The file might not exist.

The application could:

File not found
      ↓
Ask user for another file

That's a reasonable recovery scenario.

Unchecked

User user = null;

user.getName();

The solution isn't usually:

catch (NullPointerException)

The solution is to fix why user is null.

🧠 Bonus: One question interviewers LOVE

"Is Exception itself checked or unchecked?"

This one catches people.

Answer:

Exception itself is not a specific checked/unchecked distinction. The important distinction is whether the exception is under RuntimeException. Exceptions that extend Exception but not RuntimeException are checked, while RuntimeException and its subclasses are unchecked.

Think:

                 Throwable
                    |
                Exception
                /       \
               /         \
     RuntimeException    Other Exceptions
            ↓                  ↓
       UNCHECKED             CHECKED

Examples:

RuntimeException
 ├── NullPointerException
 ├── ArithmeticException
 ├── IllegalArgumentException
 └── IndexOutOfBoundsException

Other Exception
 ├── IOException
 ├── SQLException
 └── FileNotFoundException
